# PRD — HA Complete Irrigation Integration

> *This was generated by AI during design synthesis.*

**Status:** historical — original design spec (2026-05-19); see [PRD_GAPS.md](PRD_GAPS.md) for implementation tracking
**Domain:** `complete_irrigation`
**Target HA version:** 2024.4+
**Target hardware:** Raspberry Pi 4 (4 GB+) or higher; HA OS / Container / Supervised

---

## Problem Statement

I want to control my home's irrigation system from Home Assistant with full visibility into what's running, why, and when. The official Rachio integration is a dumb relay — it can't read my soil moisture sensors, it doesn't honor my Tempest weather station, it doesn't give me a calendar of upcoming runs, and it doesn't let me build schedules that adapt to real conditions.

Existing community options either solve one piece (e.g., a smarter Rachio bridge) or require running a separate service outside HA (Docker, Node.js, cloud accounts). I want one HACS-installable integration that runs natively inside HA on my Pi 4, works with whatever irrigation controller I happen to own, takes my soil sensors as the primary input, modulates with my local weather station, and surfaces every decision so I can trust it.

---

## Solution

A Home Assistant custom integration that:

1. **Auto-detects** any installed irrigation integration (Rachio, Hydrawise, RainMachine, B-Hyve, OpenSprinkler, ESPHome, etc.) and imports its zones via HA's entity registry — hardware-agnostic.
2. **Imports moisture and temperature sensors** by device search (like HA native), auto-maps known brands (COOLO CS-201Z, THIRDREALITY Smart Soil Moisture Gen2), and tags them with an area + position label for clean UI.
3. **Categorizes each zone by plant type** (Lawn, Bushes, Vegetable Garden, Citrus, Trees, Custom) with sensible min/target/max moisture defaults sourced from horticultural guidance.
4. **Uses moisture sensors as the primary driver of runtime** when present, with weather modulating on top. When no sensor is present, falls back to weather-driven decisions.
5. **Integrates the WeatherFlow Tempest** weather station (or any HA weather entity) for hot-weather boost, system-wide rain lockout, and wind-based deferrals.
6. **Resolves scheduling conflicts** with a visual three-option picker at create-time (defer new / shift existing earlier / split the difference) and quiet-hours-aware guardrails at runtime.
7. **Exposes a dedicated HA calendar entity** with two-way edit support so users can drag, skip, or add runs from any device (browser, Companion app, Nabu Casa remote).
8. **Ships a custom panel** in the HA sidebar (full-width Lit-based UI) showing weather, today's/this-week's calendar, and per-zone status with manual-run, schedule-edit, and sensor-data tiles.
9. **Honors the HA theme engine** via CSS variables so the panel matches whatever theme the user has installed.
10. **Sends push notifications** via the HA Companion app for events the user opts into, with a full notification catalog providing per-event channel and quiet-hours controls.
11. **Provides help tooltips (ⓘ)** on every adjustable setting, with standardized content (what it does, default, range, guidance) sourced from translation files.
12. **Offers a "new grass" establishment mode** — a bounded schedule (default 3× per day × 10 min × 12 days) that pauses normal schedules during the establishment window and prompts for transition at the end.
13. **Reminds the user weekly** (dismissible) to verify watering is correct for each zone, plus a one-time 7-day post-install reminder.

## User Stories

### Installation & first-run

1. As a HA user, I want to install via HACS, so that I don't need to manually copy files.
2. As a HA user, I want a guided multi-step setup wizard, so that I don't have to edit YAML.
3. As a user with multiple controllers, I want to add the integration multiple times, so that each controller has its own configuration.
4. As a HACS maintainer, I want the integration to validate cleanly under `hassfest` and `hacs/action`, so that users get a reliable install.
5. As a user on a Pi 4, I want the integration to run at <60 MB RAM and <1% CPU steady state, so that it doesn't impact my Home Assistant.

### Controller / zone discovery

6. As a Rachio user, I want my installed Rachio integration auto-detected, so that my zones are pre-populated in setup.
7. As a Hydrawise user, same auto-detection behavior.
8. As a RainMachine user, same.
9. As a B-Hyve user, same.
10. As an OpenSprinkler user, same.
11. As an ESPHome / DIY user, I want manual switch selection with all my switches listed, so that any switch-based irrigation works.
12. As a user, I want non-irrigation switches (garage doors, lamps) clearly marked as such or suggested-excluded, so that I don't pick them by accident.
13. As a user, I want to rename zones during setup, so that they have friendly names independent of upstream device naming.
14. As a user, I want a warning that this integration replaces (not augments) my controller's native scheduling, so that I disable schedules in the Rachio app to avoid collisions.

### Moisture sensor setup

15. As a user, I want to add moisture sensors via a device-search dropdown, so that I find them like in HA native.
16. As a COOLO CS-201Z user, I want my sensor's entities auto-mapped (soil_moisture, temperature, humidity, battery), so that I don't pick from a list of 12.
17. As a THIRDREALITY user, same auto-mapping behavior.
18. As a user, I want each sensor labeled with an Area (e.g., "Garden East") and a Position (cardinal direction, color code, or custom text), so that they're identifiable in the UI.
19. As a user, I want suggested defaults from sensor names when they follow a convention (e.g., `garden_east_1` → Area "Garden East", Position "1"), so that setup is fast for sensible naming.
20. As a user with random sensor names, I want a blank form fallback, so that I'm not blocked by naming.
21. As a user, I want one sensor per zone as the default, so that simple setups are simple.
22. As a user, I want the option to assign multiple sensors per zone with a combine policy (Average / Lowest / Highest / Primary+info), so that I can spread probes across an area.
23. As a user, I want to access a sensor's calibration via HA's device page (one click from the panel), so that calibration uses standard HA UX.

### Plant categories & moisture targets

24. As a user, I want to assign a plant category to each zone, so that I get horticulturally-sensible moisture defaults.
25. As a user, I want to see explanatory text for each category in a popup, so that I understand the source of the defaults.
26. As a power user, I want to override the min/target/max moisture per zone, so that I can tune for my specific plants.
27. As a user with unusual plants, I want a Custom category, so that I can set my own ranges.

### Scheduling

28. As a user, I want to create rules with interval semantics (every N days, every X hours, specific days of the week), so that I match my watering plan.
29. As a user, I want to set a specific start time per rule, so that runs happen at optimal hours.
30. As a user, I want to set a base duration per zone per rule, so that each zone runs the right amount.
31. As a user, I want to temporarily disable a rule, so that I can skip without deleting.
32. As a user, I want sensor-driven runtime adjustment using a 4-band controller (urgent if below min, mild if below target, light if below max, skip if at-or-above max), so that watering matches actual soil conditions.
33. As a user, I want the system to log every runtime decision with a reason ("Watered 22 min — moisture 18% below 21% minimum, urgent boost applied"), so that I can trust the automation.

### Conflict resolution

34. As a user creating a conflicting schedule, I want a popup with visual timeline previews of each resolution option, so that I see the result before committing.
35. As a user, I want three options: (A) defer the new one, (B) shift existing earlier to make room, (C) split the difference (both yield equally), so that I can pick what fits.
36. As a user, I want a "Cancel and pick a different time" button, so that I have an escape hatch.
37. As a user, I want a "Always use this option" checkbox, so that future conflicts auto-resolve my preferred way (reversible in Options).
38. As a user, I want a 2-minute auto-buffer between back-to-back zone runs, so that valves have time to settle.

### Runtime conflicts (sleep)

39. As a user, I want small shifts (<15 min) to be absorbed silently and logged only, so that I'm not nagged for minor adjustments.
40. As a user, I want configurable quiet hours (default 10 PM – 7 AM), so that I'm not woken for non-critical events.
41. As a user, I want cascading delays capped (default: 2 hours past original time, or 3 deferrals in a day), so that runs don't get pushed indefinitely.
42. As a user, I want a consolidated morning summary at the end of quiet hours, so that I can review overnight activity at a glance.
43. As a user, I want hard failures (zone won't start, controller offline) to push immediately regardless of quiet hours, so that I know about real problems.
44. As a user, I want the option to silence hard failures and roll them into the morning summary, so that I'm in control.

### Weather integration

45. As a user, I want my installed Tempest integration auto-detected, so that weather "just works."
46. As a user without Tempest, I want HA's default weather entity used as a fallback, so that basic rain/temp logic still works.
47. As a user, I want rainfall to trigger a system-wide lockout with tiered duration (4h / 6h / 12h / 24h based on rainfall total), so that I don't water after rain.
48. As a user, I want lockout thresholds and durations editable in Options, so that I can tune for my climate.
49. As a user, I want a visible "rain lockout active until X" banner with a "resume now" override, so that I can intervene if needed.
50. As a user, I want hot weather boost (>100°F by default), so that plants survive heat waves.
51. As a user, I want the hot temp threshold and boost % configurable, so that I tune for my climate (with °F / °C following HA's unit preference).
52. As a user, I want wind speed to defer runs, so that wind doesn't waste water via drift.

### Notifications

53. As a user, I want push notifications via the HA Companion app, so that I get alerts on my phone.
54. As a user, I want per-event control (on/off, channel, quiet-hours behavior) for ~25 notification types, so that I can mute the noisy ones.
55. As a user, I want notification events fired as typed HA events (e.g., `complete_irrigation.notification`), so that I can wire automations for advanced routing (Slack, email, etc.).
56. As a user, I want a "test notifications" button in Options, so that I can verify my phone setup.
57. As a user, I want sensor-offline and sensor-below-minimum events to push immediately, so that broken sensors don't silently degrade watering.

### Calendar

58. As a user, I want a dedicated HA calendar entity (`calendar.complete_irrigation`), so that I can see upcoming runs.
59. As a user, I want two-way edit: drag in the HA calendar dashboard to shift a run, delete to skip, add an event to create a one-off run, so that the calendar acts like a calendar.
60. As a user, I want rule changes (interval, conditions) to remain in the panel only, so that the source of truth is clear.
61. As a user, I want an iCal feed URL, so that I can subscribe from my phone's native calendar app (read-only).

### Custom UI panel

62. As a user, I want a custom panel in the HA sidebar, so that I have a dedicated UI without installing extra HACS frontend cards.
63. As a user, I want the panel to follow my HA theme via CSS variables, so that it matches my dashboard's look.
64. As a user, I want a full-width layout, so that I see everything at once.
65. As a user, I want a weather header showing temp, humidity, feels-like, heat index (computed), rainfall, wind, sunrise, sunset, UV, so that I know what's happening outside.
66. As a user, I want a calendar view with today / this-week toggle, so that I can see runs at different scales.
67. As a user, I want per-zone tiles showing on/off status, current moisture (with sensor breakdown if multiple), soil temp, humidity, manual-run button, edit-schedule button, and calibration shortcut, so that the dashboard is fully operational.
68. As a user, I want everything also exposed as standard HA entities, so that I can build my own Lovelace dashboards if I prefer.

### Help tooltips

69. As a user, I want ⓘ help icons on every adjustable setting, so that I know what each thing does.
70. As a user, I want tooltip content following a standardized format (title, explanation, default, range, guidance), so that I can adjust intelligently.
71. As a translator, I want tooltip text in the integration's translation files, so that the integration can be localized.
72. As a user on mobile, I want tooltips to be tap-to-open, so that touch devices work properly.

### "New grass" establishment mode

73. As a user planting new grass, I want a "New grass" preset button, so that I get an aggressive establishment schedule with one click.
74. As a user, I want to set cycles/day, duration per cycle, and total days for the establishment, so that I can tune to my seed.
75. As a user, I want my normal schedule paused during establishment, so that I don't over-water.
76. As a user, I want a prompt at the end of establishment ("continue / extend / switch to normal"), so that I transition cleanly.
77. As a user, I want establishment runs to bypass moisture min/max (they'll naturally be wet), so that the bounded schedule actually runs.

### Verification reminders

78. As a new user, I want a one-time 7-day post-install reminder ("Is watering working?"), so that I check the initial setup.
79. As a regular user, I want a weekly verification reminder (Sundays, configurable), so that I can dismiss or review.
80. As a user, I want the reminder shown per-zone with stats (runs in last 7 days, avg moisture, target), so that I can spot drift.
81. As a user, I want a "snooze 30 days" option on the reminder, so that I can opt out temporarily without losing the feature.

### Manual run control

82. As a user, I want a "Run now" button per zone tile, so that I can test or manually water.
83. As a user, I want a duration popup that pre-fills with 10 minutes by default, so that quick test runs don't waste water.
84. As a user, I want to customize the manual-run default, so that my preferred test duration sticks.

### Sensor calibration access

85. As a user, I want a calibration shortcut button on each zone's sensor display, so that I can open HA's device page in one click.

## Implementation Decisions

### Architecture

The integration follows a **deep-module** architecture so the business logic is testable in isolation and the HA-facing layer stays thin.

**Deep modules** (pure logic, no HA dependency, no I/O — testable as pure functions):

- **`ScheduleStore`** — CRUD for rules. Persistence via HA storage helper. Pure data, no clock awareness.
- **`RunPlanner`** — Given `(rules, now, sensors, weather)` → ordered list of planned runs for the next N days. Same inputs → same outputs.
- **`ConflictResolver`** — Given a list of planned runs → resolved schedule respecting "one zone at a time" + 2-min buffer. Implements all three resolution policies (A defer / B shift / C split).
- **`MoistureGate`** — Given `(planned run, sensor readings, target thresholds)` → adjusted runtime or skip with reason. 4-band controller.
- **`WeatherGate`** — Given `(planned run, weather snapshot)` → skip reason / runtime adjustment / pass-through. Honors rain lockout, hot-weather boost, wind threshold.

**Shallow adapters** (HA glue — just adapters, no logic):

- `__init__.py` — entry point, sets up coordinator and platforms
- `config_flow.py` — multi-step setup wizard
- `sensor.py` — status sensors (`sensor.next_run`, `sensor.active_zones`, `sensor.rain_lockout_until`)
- `switch.py` — control entities (`switch.pause_all`, `switch.skip_today`)
- `calendar.py` — HA Calendar platform implementation (two-way edit)
- `services.py` — exposed HA services (`run_zone`, `pause`, `resume`, `create_rule`, etc.)
- `coordinator.py` — DataUpdateCoordinator that ticks every minute and drives the deep modules

**Frontend** (Lit, bundled with the integration):

- `frontend/complete-irrigation-panel.js` — single custom panel, full-width, registers as a sidebar item

### Tech stack

- **Python 3.12** (HA minimum)
- **Voluptuous** for config schema validation (HA standard)
- **Lit** for the frontend panel (HA core uses Lit; native theming, no extra runtime)
- **HA storage helper** for rule + notification preferences persistence (NOT a separate SQLite)
- **No external dependencies** at runtime — uses HA's HTTP, WebSocket, and entity APIs

### Defaults captured in code

`const.py` already encodes:
- Plant categories with min/target/max + info text
- Conflict resolution policies, 2-min buffer
- Quiet hours (10 PM – 7 AM)
- Small-shift tolerance (15 min)
- Cascade caps (2 hours / 3 deferrals)
- Manual-run default (10 min)
- Hot weather threshold + boost (100°F / +25%)
- Rain lockout tiers (0.10/4h, 0.25/6h, 0.50/12h, 1.00/24h)
- New grass defaults (3 × 10 min × 12 days)
- Sensor combine modes (average / lowest / highest / primary)

### Testing strategy

Tests target the **deep modules** through their public interfaces (integration-style, not implementation-coupled). Per the TDD skill: one test → one implementation, vertical not horizontal.

**Recommended for v1 test coverage:**

1. `RunPlanner` — plan generation across rule types, sensor inputs, weather snapshots
2. `ConflictResolver` — all three policies, multi-way conflicts, back-to-back zones, midnight crossings
3. `MoistureGate` — 4-band controller behavior across each band, multiple-sensor combine modes
4. `WeatherGate` — rain lockout activation/expiry, hot-weather boost, wind defer

**Not in v1 test scope** (revisit later):
- Config flow steps (manual QA in MVP)
- Calendar two-way edit (manual QA in MVP)
- Frontend panel (visual QA in MVP)

### Open architecture questions for prototyping

Before any production code, two throwaway prototypes per the `prototype` skill:

1. **`ConflictResolver` (LOGIC branch)** — terminal app that pushes the state machine through weird scenarios (3-way overlap, cascading deferrals, midnight crossings) to validate the resolution policies before committing.
2. **Panel layout (UI branch)** — three radically different layouts (single column / sidebar nav / tabbed) on a single route, switchable via `?variant=` param. Pick the winner before implementing.

### What's explicitly out of scope for v1

- Multi-language UI (English only at v1, translation infrastructure included)
- Smart Hose Timer program management beyond zone switches
- Direct Rachio/Hydrawise/etc. API calls (we go through HA's existing integrations)
- Cloud sync of configuration (everything lives in HA, backed up with HA snapshots)
- Mobile app of our own (HA Companion app + Nabu Casa covers mobile)
- Soil moisture sensor calibration UI (use HA's device page — see story 85)
- Pressure / flow rate sensors (water meter integration — Phase 2)
- Anomaly detection ("zone ran but moisture didn't change") — Phase 2
- ET-based runtime adjustment using solar radiation curve — Phase 2
- Voice control beyond what HA's own assistant provides — Phase 2

## Acceptance criteria for v1.0

- [ ] Integration installable via HACS (`hassfest` + `hacs/action` validations pass)
- [ ] Config flow runs to completion with one Rachio + one Tempest + one COOLO sensor
- [ ] At least one rule can be created from the panel
- [ ] Created rule fires at the scheduled time and turns the zone on/off
- [ ] Conflict popup appears and resolves correctly across all three options
- [ ] Moisture sensor below minimum → urgent boost runtime; above max → skip
- [ ] Rain detected → system-wide lockout banner shown, runs skipped
- [ ] Hot weather → runtime boosted by configured %
- [ ] Calendar entity shows next 14 days of planned runs
- [ ] Push notification fires for at least one event category (e.g., morning summary)
- [ ] Custom panel loads in the sidebar, follows HA theme, displays weather + calendar + zone tiles
- [ ] Help tooltips appear on every adjustable setting in Options
- [ ] Pi 4 (4 GB) sustained CPU < 5% with 4 zones + 3 sensors
